# Einfach 文档与官网规范

> 版本：1.3
> 基线日期：2026-07-30
> 目标：让陌生开发者与 AI 在十分钟内理解 Einfach、跑起示例并找到准确 API

## 1. 这次要交付什么

Einfach 当前优先建设两个直接面向使用者的成果：一套可维护的文档规范，以及一个能
展示真实能力的静态官网。它们服务于同一个使用路径：**认识项目 → 判断适配性 → 复制
示例 → 查找 API → 在自己的项目中开始使用**。

本规范不把行为准则、供应链、治理流程等长期事项混入本阶段验收；这些可以随后按实际
维护能力另立计划。

## 2. 对外信息架构

| 入口           | 任务           | 必须回答的问题                                       |
| -------------- | -------------- | ---------------------------------------------------- |
| 根 `README.md` | 快速判断与安装 | 这是什么、为什么选它、装哪个包、最小代码怎么写       |
| 官网首屏       | 传达项目优势   | 原子状态为何简单、框架支持哪些、核心能力能否一眼看见 |
| 交互演示       | 建立使用直觉   | 异步与同步 atom 如何读写、派生和暴露状态             |
| API 导览       | 快速定位能力   | 我需要的包、导出和最小用法在哪里                     |
| `docs/` 主题页 | 解决较深问题   | 异步、历史记录、表单、迁移与框架差异如何处理         |

根 README 是决策页而不是 API 手册；官网是浏览入口而不是重复 README；主题文档解释
一个概念或场景，不成为无结构的笔记集合。**本阶段以 AI 可读性为第一优先级**：视觉、
文案与站点结构都应帮助使用者或编码代理精确推导状态关系，而不是只制造印象。

## 3. 首页信息标准

官网首页按以下顺序组织：

1. **一句话定位。** 说明 Einfach 用命名 atom 表达事实，用派生 atom 表达确定的依赖关系。
2. **异步衍生契约。** 首屏后的第一个内容区必须先展示 source atom 到 `atom(async (get) => ...)`
   的异步衍生关系；`loadable` 只能作为 UI 适配层，再展示 `loading`、`hasData`、`hasError`。
3. **核心状态模型。** 明确展示：组件可直接按 atom 读取而非传递 props；命令 atom 如何
   用 `getter` 读取任意关联状态、用 `setter` 写入必要状态；状态颗粒度小如何让需求变更保持局部。
4. **同步状态契约。** 首页必须可见地列出一个示例的可写输入、派生规则、只读输出与受影响
   视图；这些信息不可藏在动画或折叠面板后。
5. **真实交互演示。** 页面自身必须使用 `@einfach/react` 的 `atom`、`Provider`、`useAtom`
   和 `useAtomValue`，不可用 `useState` 伪造状态库行为。
6. **API 导览。** 以包为单位提供导出、用途、状态角色和最小片段；只展示已经从包入口
   确认的 API。
7. **下一步行动。** 明确提供 npm 安装命令、仓库地址和本地开发指令。

页面应适配窄屏，按钮有焦点样式，文本对比度足够，代码块可读；视觉可以大胆，但不能
以动画、图片或大段标语掩盖使用信息。

## 4. API 文档标准

每一个公开 API 条目包含以下最小信息：

| 字段         | 要求                                                                          |
| ------------ | ----------------------------------------------------------------------------- |
| 所属包       | 使用完整 npm 包名，如 `@einfach/react`                                        |
| 名称与签名   | 以 TypeScript 导入和最小调用展示，不猜测内部路径                              |
| 一句话用途   | 说明它解决的用户问题，而非复述类型名                                          |
| 最小示例     | 可独立理解，命名与 README 保持一致                                            |
| 状态角色     | 明确它是源状态、派生状态、读取绑定、写入绑定或工具                            |
| 异步协议     | 列出 source atom、异步衍生规则与 UI 适配后的 `loading`、`hasData`、`hasError` |
| 限制或关联项 | 需要 `Provider`、与核心 API 的关系或适用框架                                  |

API 数据要集中维护，界面组件不内嵌散落的 API 文案。新增或删除公开导出时，同一 PR
必须更新 API 数据、包 README 和必要的主题文档；文档错误按用户可见 bug 处理。

## 5. 异步衍生演示标准

异步衍生是首页主路径，不是后续补充。主模型是 `atom(async (get) => ...)`：它读取一个或多个
source atom，并把 Promise 作为衍生结果。`createAsyncParamsAtom` 适用于把外部参数直接包装为
可写异步 atom 的场景，但不应遮蔽“由哪些状态派生”的关系。React/Solid 侧的 `loadable` 只是把
已经存在的异步衍生结果映射为可渲染状态，并不创建业务上的异步衍生。

演示至少包含成功、加载和错误三种可操作结果，且必须标出：命令 atom 写入了哪个 source atom、
异步衍生 atom 读取了哪些 atom、`loadable` 如何被 UI 消费。

```ts
const requestAtom = atom({ userId: '42', revision: 0 })

const userAtom = atom(async (getter) => {
  const request = getter(requestAtom)
  return fetchUser(request.userId)
})

const refreshUserAtom = atom(null, (getter, setter, userId: string) => {
  const current = getter(requestAtom)
  setter(requestAtom, { userId, revision: current.revision + 1 })
})

const userViewAtom = loadable(userAtom) // 仅 UI 适配

// UI 读取 { state, data?, error? }
```

不要并行维护 `isLoading`、`error`、`data` 三个组件局部状态；它们应来自同一个异步衍生 atom
经视图适配后的可观察结果。

## 6. 同步派生演示标准

演示必须体现真实而小的状态流，推荐固定为“源 atom → 操作 → 派生 atom”：

```ts
const countAtom = atom(3)
const doubledAtom = atom((get) => get(countAtom) * 2)
```

使用者点击加减后，应同时看到源值和派生值更新。演示只承担解释一个概念的职责；历史记录、
表单等复杂主题应各有独立演示，不能无限堆到首页。

所有产品状态—including 当前 API 标签、演示计数与派生展示—由 Einfach atom 管理。组件
局部的 ref、第三方控件内部状态和动画状态可按框架需要存在，但不能成为业务真相来源。

## 7. AI 可读性标准

“AI 友好”不是给页面贴标签，而是让状态模型可被可靠地重述、生成和验证。每个状态主题页
与示例都必须满足下面的契约。

| 契约字段   | 写法要求                                                       |
| ---------- | -------------------------------------------------------------- |
| 状态事实   | 命名为业务名词，并标明值类型和唯一写入点                       |
| 依赖关系   | 用 `derivedAtom = f(sourceAtom)` 描述，列出所有直接输入        |
| 写入边界   | 说明哪个 atom 可写，派生 atom 默认只读                         |
| 可验证断言 | 给出确定例子，如 `count = 3 → doubled = 6`                     |
| 框架边界   | 区分 `@einfach/core` 模型和 React/Solid 的读取、写入绑定       |
| 组件边界   | 说明组件直接读取的 atom，避免把业务状态伪装成 props 链         |
| 命令边界   | 跨 atom 更新使用 `atom(null, (getter, setter, ...args) => {})` |

避免“自动同步”“内部处理”“状态会更新”这类没有因果关系的句子；改写为“写入 X 后，Y 按
规则 Z 重新计算”。AI 生成的示例也必须先给出状态契约，再给出代码，并以 TypeScript 类型
检查和可运行演示作为最低校验。命令 atom 必须解释读取了哪些 atom、写入了哪些 atom，不能
把跨状态副作用藏在组件回调中。

## 8. 内容写作规范

- 先写用户结果，再写实现细节；每段只回答一个问题。
- 示例优先 TypeScript，并使用复制后不需脑补的变量名。
- 页面文案、README 和包文档采用一致术语：`atom`、`store`、`Provider`、派生 atom。
- 需要跨组件共享的状态由消费者直接读取 atom；props 仅传递组件配置或一次性展示数据。
- 跨 atom 写入优先声明为命令 atom：`atom(null, (getter, setter, ...args) => {})`。
- 状态按需求边界保持小颗粒度；新需求先新增独立 source atom 或 derived atom，让改动只沿局部依赖链传播，避免把无关字段塞进既有大对象。
- 清楚标记实验性 API 与框架差异；没有证据不写性能、兼容性或稳定性承诺。
- 每个页面给出一个下一步链接或命令，避免让读者在阅读完后失去路径。

## 9. 站点工程规范

官网位于 `apps/site`，使用 Vite 构建为纯静态产物。源文件按职责拆分：

| 文件范围           | 唯一职责                 |
| ------------------ | ------------------------ |
| `src/siteAtoms.ts` | 官网交互状态             |
| `src/api-reference/` | 按包维护的 API 参考数据 |
| `src/components/`  | 单个页面区块的呈现与交互 |
| `src/App.tsx`      | 首页区块编排             |
| `src/styles/`      | 按页面区块拆分的视觉系统 |

普通文件保持在 300 行以内；站点不可为展示便利绕开 `@einfach/react`。开发与生产构建
分别使用 `pnpm docs:dev`、`pnpm docs:build`；CI 在 Node 20 任务中执行站点类型检查和构建。
