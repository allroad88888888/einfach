# Rust `bulk_import_cells` perf — phase decomposition

## Headline

The Rust `bulk_import_cells` path spends **82-91% of wall-clock time in
the post-loop flush phase** — `WorkbookLoader::flush` +
`Sheet::bulk_load::flush` (dirty-BFS through formula dependents +
cross-sheet BFS + subscriber notify dedup). Engine parser cost,
per-formula dep-graph wiring, and the wasm-bindgen boundary are each
<10% of the budget across every tier measured.

| Tier | total cells | JS wall (ms) | flush (ms) | flush % | engine total (ms) |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 100k | 100 000 | 10 523 | 9 552 | 90.8% | 10 367 |
| 250k | 250 000 | 20 703 | 17 112 | 82.7% | 20 064 |
| 500k | 500 000 | 40 602 | 36 734 | 90.5% | 40 006 |

(One run per tier, `solid/excel/test/perf-rust-bulk-import-trace.bench.ts`;
median of multiple runs would be cleaner but the 100k tier alone takes
~10s and three tiers fit a 90s budget. The 250k tier is a noisy
single-sample outlier on share-of-wall — see "Super-linearity" below.)

The 1M tier is NOT in the table: the instrumented variant exhausts
wasm32 linear memory before the load completes (the two-pass write
shape + per-formula string clone roughly doubles peak alloc versus
production `bulk_import_cells`, which is what the headline 108× claim
in `solid/excel/test/perf-ts-vs-wasm-report.md` measured). Production
`bulk_import_cells` at 1M completes in ~98 s; extrapolating the 500k
breakdown linearly puts flush at ~73 s of that — comfortably the
dominant phase even at 1M scale.

If we want the Rust path competitive with the TS engine at multi-million
cells, **the flush BFS is where the optimization budget goes**.

## Phase taxonomy

```
JS wall (around the RPC) ─┬─ rpc_deserialize_ms     (serde_wasm_bindgen)
                          │
                          ├─ engine_total_ms       (workbook.bulk_load(...))
                          │   ├─ set_cell_loop_ms       (loader.set_cell for primitives)
                          │   ├─ set_formula_loop_ms    (loader.set_formula for formulas —
                          │   │                          includes engine-side parse, cycle
                          │   │                          check, dep-graph edge install,
                          │   │                          AST storage)
                          │   └─ flush_ms               (WorkbookLoader::flush +
                          │                              per-sheet BulkLoader::flush:
                          │                              dirty BFS + cross-sheet BFS +
                          │                              subscriber notify dedup)
                          │
                          └─ unaccounted_ms        (wasm-bindgen boundary,
                                                    JS-side V8 array build,
                                                    Date.now drift)

(side channel) parse_only_ms — isolated re-parse pass over every formula
                                string, AST discarded. Measures bare
                                parser cost separately from the engine.
                                Does NOT contribute to engine_total.
```

`set_cell_loop` and `set_formula_loop` deliberately do NOT interleave
in caller order (production `bulk_import_cells` does interleave). The
bench workload puts seeds in column A and formulas in cols B/C/D, so
the order swap is invisible. Hosts needing order-preserving import use
the production `bulk_import_cells` entry point.

### Reading the numbers

- **Flush dominates at every measured tier**: 90.8% / 82.7% / 90.5%.
  The 250k dip to 82.7% is one-sample noise — `set_formula_loop` on
  that run came in at 13.7% (vs ~8% at the other tiers), which dragged
  the share down. Median over 3+ runs would smooth this; the absolute
  flush number (17.1 s) still dwarfs every other phase.
- **Parser is not the bottleneck.** Isolated parse-only takes ~0.7
  µs/formula. The whole `set_formula_loop` is mostly NOT parse — it's
  the `FormulaRecord` build, the same-sheet `would_create_cycle`
  static check, the cross-sheet edge install into `CrossSheetDeps`,
  and the `touched.insert`.
- **Cell storage is free.** 17-109 ms across 50k-250k primitives = 0.3
  µs/cell. Not a target.
- **Deserialize is fast.** `serde_wasm_bindgen::from_value` clocks 1-2%
  of the wall. The wasm-bindgen boundary itself (`unaccounted`) is
  <1%. The RPC `postMessage` round-trip is paid by the host bench
  separately (not measured here); the JS-side wall-clock around
  `bulkImportCellsInstrumented` already includes the JsValue marshal.

## Super-linearity

Cell-count ratio from 100k → 500k = 5.00×. A perfectly linear phase
also grows 5×; >5× = super-linear (worse than work growth), <5× =
sub-linear (engine has overhead that amortizes).

```
Phase             | 100k    | 500k    | Ratio  | Verdict
------------------|---------|---------|--------|------------
deserialize       | 110     | 457     | 4.15×  | sub-linear
parse-only        | 34      | 117     | 3.44×  | sub-linear
set_cell loop     | 17      | 49      | 2.88×  | sub-linear
set_formula loop  | 798     | 3223    | 4.04×  | sub-linear
flush             | 9552    | 36734   | 3.85×  | sub-linear
engine total      | 10367   | 40006   | 3.86×  | sub-linear
JS wall           | 10523   | 40602   | 3.86×  | sub-linear
```

**Finding**: at the measured scale (100k → 500k cells), every phase
is **sub-linear** in `cell_count`. The "gap widens super-linearly with
scale" claim from `perf-ts-vs-wasm.bench.ts` (where WASM/TS ratio went
44× → 69× → 108× as cells went 10k → 100k → 1M) is therefore caused
by the **TS side scaling SUPER-linearly down** (TS `bulkApply` is
faster at scale due to broad-invalidation savings on its broad-Map-
clone model), not the Rust side getting slower at scale.

That said, sub-linear does NOT mean Rust is fine — Rust's absolute
time per cell is much higher than TS's, and *most* of the absolute
time is in flush. So the "where do we cut?" answer is still: flush.

There IS a noisy super-linear blip at the 250k tier (flush 250k →
500k ratio = 2.15× for 2× more cells — mildly super-linear). Whether
that holds with median-of-3 sampling needs follow-up; the 100k →
500k 5×-to-3.85× signal is the more trustworthy headline.

## Why flush is so expensive (engine code reading)

`BulkLoader::flush` in `rust/excel-core/src/sheet.rs` (line ~2997):

```rust
let mut dirty: HashSet<CellAddress> = HashSet::new();
let mut stack: Vec<CellAddress> = Vec::new();
for &addr in &self.touched {                 // |touched| = N cells
    stack.extend(self.sheet.dependents_of(addr));  // allocates HashSet
}
while let Some(addr) = stack.pop() {
    if !dirty.insert(addr) { continue; }
    if let Some(record) = self.sheet.formula_cells.get(&addr) {
        *record.cache.borrow_mut() = FormulaCache::Dirty;
    }
    stack.extend(self.sheet.dependents_of(addr));  // again
}
```

`Sheet::dependents_of(addr)` (line ~938) per call:

1. Clones `cell_dependents[addr]` into a fresh `HashSet<CellAddress>`.
2. Iterates `range_dependents.candidates_for(addr)` (Track E's
   bucket-by-range index, capped per call by `is_wide` cutoff at 4096
   rows or cols).
3. For each candidate range containing `addr`, extends the set with
   `formulas_for(range)`.

Cost shape at the bench workload (50%-30%-20% binop/IF/SUM mix):

- Per-touched-seed (column A), `cell_dependents` has ~1 entry on
  average (the binop formulas reference 2 specific cells out of
  ~`seedCount`).
- Per-touched-seed, `candidates_for(addr)` returns ~100 SUM ranges
  (20% of formulas are SUMs with average length ~512, distributed
  over `seedCount` seeds).
- So `dependents_of` does ~100 range-membership checks + ~10k
  formula-set additions per seed.

At 500k touched seeds × ~10k extensions = ~5e9 extension steps.
That's the source of the 36s flush at 500k. Each call also allocates
a HashSet — at 500k cells that's at least 500k allocs just for the
initial walk.

Note: the BFS visits each formula at most once (via the outer `dirty`
HashSet for dedup). But it CALLS `dependents_of` on each newly-dirty
formula too, which is another N calls returning empty sets (formulas
in this workload don't have downstream formulas). Each empty
`dependents_of` still allocates a `HashSet` and walks
`range_dependents`.

## Recommended next perf intervention

Target the flush BFS, in priority order:

1. **Stop allocating a fresh `HashSet` per `dependents_of(addr)` call.**
   The BFS already maintains an outer `dirty` HashSet for dedup;
   `dependents_of` should take `&mut HashSet` (or `&mut Vec` with
   manual dedup) and push into it directly. Saves at least one
   `HashSet::new()` + clone per BFS step. Tight diff; semantics
   preserved.

2. **Coalesce range-dependent lookups across the touched set.** Today
   each touched cell does an independent `candidates_for(addr)` walk
   over `range_dependents`. With N touched cells you do N candidate
   walks, each returning ~100 ranges. A single pass — iterate every
   range in `range_dependents` once, intersect with `touched`, mark
   every formula in matched ranges dirty in one go — flips inner
   complexity to `O(|ranges| + |formula_ids|)` regardless of
   `|touched|`. At the bench's shape that's 5e9 → 5e7 steps. Needs a
   `touched`-membership predicate that's cheap (HashSet contains).

3. **Defer dirty-marking to first read.** Mirror the TS engine's
   approach (see `vanilla/excel-core-ts/docs/PLAN.md §4.1`): the
   per-cell `FormulaCache::Dirty` flip happens at the next read of
   that cell instead of during import. Drop the "compute dirty
   closure during flush" step entirely and rely on the
   `FormulaCache::Dirty` check at eval time. Bigger refactor — affects
   subscriber-notify-dedup semantics on import (subscribers wouldn't
   fire eagerly post-import; this might be a feature, not a bug, for
   bulk paths).

Recommend starting with **(1) — instrumented bench rerun + cargo flame-
graph would confirm the alloc-per-call hypothesis is the dominant
cost**. Then evaluate (2) vs (3). (3) gives the largest theoretical
speedup but is the biggest behavior change.

Not recommended:

- **Speeding up the parser.** Already <1% of wall; not a target.
- **Speeding up `set_formula` dep-edge install.** ~8% at the
  measured tiers, and the savings would be marginal.
- **Reducing wasm-bindgen marshaling.** ~1% combined for
  deserialize + unaccounted.
